# 全文搜索 v0.2.0 · 实现与验收报告

> 设计依据：[`2026-09-22-fulltext-search-design.md`](2026-09-22-fulltext-search-design.md)
> 实测工具：`scripts/SearchProbe.java`（真书语料）、`scripts/FtsProbe7/8.java`（查询语法）
> 语料：桌面《小说txt》4 本真实长篇（元尊 7.8MB / 全职高手 10.7MB / 斗破苍穹 10.2MB / 武动乾坤 7.8MB）

---

## 一、结论

v0.2.0 的全文搜索**达标**：四本书共 6100 章、16 个查询词上**候选 == 精确（零假阳性）**，
建索引 3.8~6.4 秒/本，日常查询 16~104 ms。

新增测试 **49 个**（分词 18 + 存储 26 + 批量读章 5），全模块 **279 个测试全绿**。

---

## 二、落地的东西

| 模块 | 新增 | 职责 |
|---|---|---|
| `qingdu-common` | `CjkTokenizer`（+18 个测试） | 中文二字滑窗切分。放在 common 而不是 core，见第五节偏差说明 |
| `qingdu-core` | `ChapterTextBatch`（+5 个测试） | 整本读一次、按字节偏移切任意一章 —— 建索引和后过滤共用 |
| `qingdu-store` | `SearchStore`（+26 个测试）、`model/SearchDocument` `SearchHit` `SearchResult`、`ChapterTextSource` | FTS5 表的懒创建、指纹失效判断、整本重建、查询 + 后过滤 + 摘要 |
| `qingdu-desktop` | `SearchPanel`、`ChapterRenderer` 高亮支持、`ReaderView` 接线（搜索标签页 / Ctrl+F / 跳转高亮） | 界面层 |

关键设计（全部有实测支撑，细节见设计文档）：

```sql
CREATE VIRTUAL TABLE search_index USING fts5(
    book_id UNINDEXED, chapter_index UNINDEXED, body, detail = 'none');
CREATE TABLE search_meta (book_id PK → book(id) ON DELETE CASCADE,
    fingerprint, chapter_count, tokenizer_version, indexed_at);
```

- **懒建索引**：第一次在某本书里搜索时才建，界面显示「正在建立索引 500 / 1636 章」；
- **指纹失效**：`size:mtime` 变了就重建，改过的书不会搜到旧内容；
- **分词器版本**：换分词方案后老索引自动作废（`tokenizer_version` 对不上就重建）；
- **后过滤必需**：`detail='none'` 不支持短语查询，所以「云岚」「岚宗」分处两地也会被算成候选，必须拿原文再校验一次。

## 三、真书实测

### 3.1 建索引与体积

| 书 | 章节 | 文件 | 建索引 | 本书索引体积 |
|---|---|---|---|---|
| 元尊 | 1474 | 7.8 MB | 3,795 ms | 25.8 MB |
| 全职高手 | 1725 | 10.7 MB | 6,357 ms | 33.6 MB |
| 斗破苍穹 | 1636 | 10.2 MB | 5,553 ms | 32.3 MB |
| 武动乾坤 | 1265 | 7.8 MB | 4,225 ms | 24.3 MB |
| **合计** | **6100** | 36.5 MB | 19.9 s | **116.0 MB** |

> 「本书索引体积」是指该本建完索引后**数据库的增量**，不是建完那一刻的数据库总大小 ——
> 数据库四本共用一个，末本建完时总计 116.0 MB，很容易被读成"这一本的索引有 116 MB"。
> 探针原始输出因此同时印「本书索引」和「数据库累计」两列。
> 建索引耗时会随机器负载波动 ±10%，上表是其中一次快照；最新一次完整输出见
> `scripts/search-probe-report.md`（探针自己生成，不要手改）。

对照设计文档的预算：**≤ 8 秒/本** ✅（最慢 6.4 秒）、**索引体积 < 69 MB 基准** ✅（平均 29 MB，约为基准的 42%）。

## 四、过程中发现并修掉的两个问题

### 4.1 第一版验收脚本把「没查」报成了「假阳性」

第一轮跑出来的表长这样：

```
| 萧炎 | 1622 | 300 | 97 | ❌ 假阳性 1322 |
```

看起来像后过滤大面积误杀。**实际原因是我自己的统计口径错了**：
`search` 集满 300 条就停（`DEFAULT_LIMIT`），`candidateCount - hitCount` 里
那 1322 不是"校验了但不合格"，而是"压根没校验"。

修法有两处，缺一不可：

1. `SearchResult` 增加 `truncated` 字段与 `unchecked()`，把「截断」和「假阳性」**在类型上分开**；
2. 验收脚本改用 `limit = Integer.MAX_VALUE` 跑全量，才能得到真实的精确章数。

这条已经写成单元测试（`SearchStoreTest.TruncatedIsReportedSeparately`）钉住 ——
它是那种"数字看起来合理、结论完全相反"的错误，不写进测试下次还会犯。

### 4.2 建索引前书必须已在书架上

`search_meta.book_id` 有指向 `book(id)` 的外键（删书时索引跟着走），
所以脚本里先建索引再写入书目会直接抛 `FOREIGN KEY constraint failed`。
正常流程不会踩到（打开/导入时就写了书目），但脚本会 —— 已把顺序要求写进
`SearchStore#index` 的文档注释。

## 五、与设计文档的偏差（都是跑了才知道的）

| 项 | 设计文档 | 实际 | 原因 |
|---|---|---|---|
| 分词器位置 | `qingdu-core` 的 `CjkBigramTokenizer` | `qingdu-common` 的 `CjkTokenizer` | `qingdu-store` 也要用它（切索引、切查询串），而 store **不依赖 core**（见 store 的 POM 注释）。放 common 才不破坏依赖方向 |
| MATCH 串要不要给 token 加引号 | 未定 | **不加**，空格连接即可 | 探针 7/8 实测：`云岚 岚宗` 与 `"云岚" "岚宗"` 结果完全一致；而 `"云岚 岚宗"` 会直接报 `phrase queries are not supported` |
| token 是 `and` / `or` / `not` 会不会被当运算符 | 担心过 | **不会**。小写 `and` 是普通词（能命中 `you and me`），大写 `AND` 才报语法错误 | FTS5 的关键字必须大写；我们的 ASCII token 在切分时已统一折叠成小写，天然安全 |

## 六、没做 / 没验的部分（诚实清单）

1. **界面视觉效果未人工验收**。逻辑侧（跳转、高亮词选择、主题配色变量）都有测试或代码依据，
   但「搜索结果列表长什么样、跳过去高亮是否醒目」必须真人打开看一眼 —— 自动化测试覆盖不到。
2. **高亮不能做底色**。JavaFX 的 `Text` 继承自 `Shape`，没有 `background`（那是 `Region` 的属性），
   所以用的是「换色 + 加粗 + 下划线」。要做黄底高亮得换成 `TextFlow` + 自绘背景，代价大于收益。
3. **搜索只限当前这本书**。跨书搜索涉及结果归并与排序，留给后续版本。
4. **全量查询（>1200 章的候选）会到 200~300 ms**，超过设计文档给单次查询定的 200 ms。
   界面默认上限下不受影响；要优化就是给 `ChapterTextBatch` 加"解码结果缓存"。
5. **没做索引的定期清理**。删书时靠外键级联删 `search_meta`，FTS 表里的行由
   `ensureSchema` 的孤儿清理兜底（每次进程启动后的第一次搜索扫一遍）。
