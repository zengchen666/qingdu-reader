# v0.3 设计文档：书库整理 + 全库检索

日期：2026-10-02
上一版：v0.2.1（界面打磨）

---

## 〇、这一版在做什么

v0.1 ~ v0.2.1 做的是"**把一本书读顺**"：打开、分章、翻页、搜索、换肤。
v0.3 转向"**把书库管起来**" —— 书架上有了几十本书之后，真实需求才出现：

| 需求 | 痛点 | v0.3 的答案 |
|---|---|---|
| 书多了不知道哪本是哪本 | 书架只能按最近打开排序 | **分组**（`book.group_name`）+ 书架筛选 |
| 读到某句话想记住位置 | 书签只有标题，忘了为什么标记 | **书签备注**（`bookmark.note` 早已建好列，这次接上界面） |
| 想知道自己读了多久 | 没有数据 | **阅读时长**（按会话累积，可按天/按书看） |
| 想搜"这四本书里谁提过云岚宗" | 一次只能搜一本书，挨本搜九遍 | **全库检索**（跨书 FTS + 按书分组结果） |

**明确不在这一版里**：AI 能力（问答、摘要、人物关系抽取）。
理由不是做不动，是**它会把"本地确定性工具"变成"依赖网络与模型的服务"**，
对一个宣称"本地优先、断网可用"的阅读器是相悖的。真要做也应该做成可选增强，而不是核心路径。

## 一、schema 迁移：v1 → v2

### 1.1 迁移了什么

```sql
ALTER TABLE book ADD COLUMN group_name       TEXT;                      -- 可空，NULL = 未分组
ALTER TABLE book ADD COLUMN reading_millis   INTEGER NOT NULL DEFAULT 0;
CREATE TABLE reading_session (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    book_id    TEXT    NOT NULL REFERENCES book(id) ON DELETE CASCADE,
    started_at INTEGER NOT NULL,
    ended_at   INTEGER NOT NULL,
    millis     INTEGER NOT NULL
);
CREATE INDEX ix_session_book ON reading_session(book_id);
```

版本号写进 SQLite 内置的 `user_version`，启动时读出来决定从哪一步开始走。

### 1.2 两个设计决定

**① 新库和老库走同一条代码路径。**

不写"新库直接 CREATE 全部、老库才 ALTER"这种双轨 —— 那样两条路径要各自测试，
而且新库的最终结构就成了"隐式知识"，没人能证明它和 ALTER 出来的结构一致。
现在的做法：新库 `user_version` 是 0，一样从 `migrateV1ToV2` 走过来。
代价是新库多做一次 `ALTER TABLE`（几毫秒），换来的是**只有一条路径需要测试**。

**② `ALTER TABLE ADD COLUMN` 前面必须先查列是否存在。**

`ADD COLUMN` 撞上已有的列会直接抛 `duplicate column name`。
"用户库里已经有这一列"是完全可能的正常情况 —— 上一版程序崩在 `ALTER` 之后、
`user_version` 之前，这次启动就会撞上。多查一次 `PRAGMA table_info` 换掉一种崩溃，不亏。

> 这是本次唯一一处"为了防崩溃而牺牲一点优雅"的地方。判断标准很简单：
> **代价能不能界面上感知**。几毫秒不可感知，一种启动崩溃很显眼。

**③ 刻意不给 `group_name` 加索引。**

书库是"几十到几百本"的量级，全表扫一遍的代价可以忽略，
而多一个索引就多一处"建库时忘了建索引"的失败点。等真的攒到几千本再说。

### 1.3 `reading_millis` 与 `reading_session` 为什么都要

单看 `book.reading_millis` 一个字段就够回答"这本书读了多久"。
那为什么还要 `reading_session` 表？

因为"**这周每天读了多久**"这个问题，一个累加字段答不了 ——
它只有总数，拆不出每天。所以两个都留：累加值是热数据（书架上直接显示），
会话表是明细（将来做统计图）。代价是每次会话多插一行。

## 二、跨书检索：把"读多少"和"读多快"分开

这是 v0.3 最有技术含量的一处，也是最容易做错的一处。

### 2.1 为什么不能"把所有书读进内存"

v0.2.0 的单书检索用 `ChapterTextBatch` —— 把**整本书**读进内存（1636 章约 10 MB）。
那是**正确**的优化：建索引和后过滤共用同一份字节，整本读一次 83 ms，比逐章开文件快 280 倍。

但同一个做法搬到跨书检索上就是**灾难**：

- 候选章分布在几十本书里，"所有书都读进内存"= 50 本 × 10 MB = **500 MB**
- 一次搜索就能把堆撑爆
- 而绝大多数候选**根本不会被校验到**（条数上限一集满就停）

为了一堆用不到的数据占 500 MB，是纯亏。

### 2.2 实际做法：回到字节偏移 + seek

分章时每章都记了 `startOffset` / `endOffset`（v0.0 就在的东西），
于是任意一章都能"seek 过去、读那几十 KB、丢掉"，不需要整本在场。

`LibraryChapterTextSource` 里三处缓存，**缺一不可**：

| 缓存 | 容量 | 为什么需要 |
|---|---|---|
| 章节表 | 每本书一份（`Map<bookId, List<Chapter>>`） | 要 seek 就得知道偏移，偏移来自分章。分章要读整个文件（200~300 ms），但读完只留几十 KB 章节表，字节立刻可回收。SQL 已按 `book_id` 排序，同一本书的候选是**连续**的，不会每章都重分一次 |
| 文件句柄 | 8（LRU） | 不缓存的话每个候选章都要 `new RandomAccessFile` + seek + close —— 这是 `ChapterTextBatch` 类注释里记的"慢的不是 SQLite，是每章一次的文件打开"，同一个坑不能再踩一次。用 LRU 限制同时打开数，否则 200 本书就是 200 个句柄（Windows 上会撞句柄上限） |
| 章节文本 | 20（LRU） | 一个查询里同一章只校验一次，所以它**不是**性能必需品。留着是因为摘要生成和精确校验都要同一段文本 |

> ⚠️ **淘汰句柄必须真关**。LRU 淘汰一个 `RandomAccessFile` 只是从 map 里移除，
> 底层文件描述符还开着 —— 跑几千次之后句柄就耗尽了。这类"资源对象放进 LRU"的坑，
> 淘汰动作就得是 `close()` 而不是 `remove()`。

### 2.3 查书走实时查询，不是启动时的快照

`LibraryIndexTask.newTextSource()` 最初把书列表做成启动时的快照 Map。看起来更省事，但那样这个源就变成
"**造出来那一刻的书库**"了 —— 用户导入一本新书之后，老源对新书一无所知，
搜出来一片空白**而且不报错**。改成 `bookId -> store.books().find(bookId)` 实时查询。

### 2.4 覆盖度：三个数字必须都报

全库搜索最危险的失败模式**不是报错，是沉默地少给结果**。
用户搜「云岚宗」得到 245 章，其中 3 本书根本没建索引 —— 界面如果不提示，
用户会以为"书里就没有"，而实际上搜了等于没搜。

所以 `LibrarySearchResult` 强制携带三个数字：

| 字段 | 含义 |
|---|---|
| `libraryBooks` | 书库一共多少本 |
| `indexedBooks` | 多少本建了索引 |
| `searchedBooks` | 真正走到后过滤的有多少 |

分三档呈现（`LibrarySearchPresenter.Coverage`）：

- `FULL` —— 全建了，搜出来的就是全部
- `PARTIAL` —— **必须提示**"有 N 本书尚未建立索引，可能搜不到其中的内容"
- `NONE` —— 一本都没建，这时该说的是"可以先建立索引"，**不是"没有找到"**

> 🔴 **一个真实的 bug**：判空书库时先查了"有没有建索引"，导致空书架落进 `NONE`，
> 界面对着一个空书架喊"有 0 本书没建索引，搜不到任何内容" —— N=0，语气却像几十本。
> 修法是先判 `libraryBooks() == 0`。
> `LibrarySearchPresenterTest` 里 `noIndexAtAllIsNotReportedAsNoResults` 和
> `emptyLibraryIsNotPartial` 钉住了这两种情况的措辞。

### 2.4.1 两条防御（针对的是真实场景，不是假想敌）

**① 用 `search_index.rowid` 做二次封顶。**

`LIMIT` 挡不住"一章正文里有一万个相同 token"这种极端情况 ——
那一条 row 就对应 20000 个候选章，一次查询能拿到几百万个 int 直接把堆撑爆。
所以候选查询除 `DEFAULT_MAX_VERIFY`（时间预算）之外，还有一层
`CANDIDATE_CHAPTER_CAP`（规模预算）钉住最坏情况。**两道预算各管一件事，都不能省。**

**② 书名映射里没有的书直接不返回。**

索引是懒建的，用户可能在"移除书"之后、`pruneOrphans` 跑之前就搜了一次。
那些行没有可显示的书名，返回它们只会让界面上出现"（未知书名）"的孤儿行 ——
那是给用户看的噪声，不是他要的答案。

### 2.5 结果分组按拼音序，不按命中数

`Collator(Locale.CHINA)` 排序。理由：找书的时候人在意"**是哪本书**"多于"哪本书命中多"。
按命中数排会把结果变成"永远那三本最厚的书在最上面"。

> ⚠️ `Collator` **不是线程安全的**（内部有缓存）。这里的做法是
> **每次排序现建一个**，方法内私有、不跨方法持有，所以不值得为它引入 `ThreadLocal`。
> 排序还带两级 tiebreaker（`bookId` → `chapterIndex`）——
> `Collator` 会把"同名书"判成相等，没有 tiebreaker 结果顺序就不确定，同一份数据两次搜索可能给出不同排列。

## 三、界面上最难的两件事

### 3.1 异步跳书：`PendingJump` 必须带 `bookId`

点《沧澜录》的搜索结果，要跳到《沧澜录》的某一章。但"打开这本书"是**异步**的
（要先 `parseMetadata` + `parseChapters`），用户完全可能在解析完之前又点了别处。

做法是记一个 `PendingJump(bookId, chapterIndex, highlight)`，等 `applyResult()` 回调时兑现，
且**只在 `bookId` 匹配时才兑现**。

- 只带 `chapterIndex` 不带 `bookId` → 点《沧澜录》会跳进当前打开的《星尘纪》，而且不报错
- 光靠 `bookId` 匹配还不够 → 还得在 `closeBook()` 里清掉 pending，
  因为"落到别的书"能挡，"书没打开却跳了一章"挡不住
- `highlightTerm` 必须在 `select()` **之前**挂上 —— 章节选择监听器是同步触发的

### 3.2 进度条：`bind` 之后不能 `setProgress`

JavaFX 的 `ProgressBar` 一旦 `progressProperty` 被 `bind`，
再调 `setProgress` 会抛 `IllegalStateException: A bound value cannot be set`。

搜索和批量建索引**共用同一条进度条**，所以两者不能并存。
`startIndexing()` 开头就用 `if (busy.get())` 挡住并发 —— 顺带也挡住了
"两个后台任务同时写同一个 SQLite 库"这种更麻烦的情况。

## 四、已定的取舍（以及为什么不再往下做）

### 4.1 跨书检索秒级，不优化

实测 555~1773 ms（4 本 / 6099 章 / 116 MB 索引），vs 单书百毫秒级。

慢的原因是明确的：单书的后过滤是"整本已在内存，`String.contains` 一下"；
跨书每校验一章是一次磁盘随机读（seek + read + decode + clean，约 0.8~1.5 ms/章），
一次查询要校验 564~1627 章。`DEFAULT_MAX_VERIFY = 2000` 是这个代价的时间预算上限。

**已决定接受这个耗时。** 理由：

1. 真实场景是"书架上有几十本小说"，一次性搜几十本书本来就该给点反馈时间
2. 已经在后台线程跑，界面不卡
3. 更快的做法（按偏移批量连续读、或给跨书单独降 `DEFAULT_LIMIT`）
   都是**用正确性或覆盖面换速度**，与"零假阳性"这个已验证的卖点冲突
4. 秒级是可解释的取舍，不是缺陷 —— 诚实写进文档比偷偷优化掉更诚实

### 4.2 章节表缓存只在同一个源对象内有效

类的注释写着"分章的代价只付一次"，但如果每次搜索都 `new` 一个源，
缓存的生命周期就完全相反 —— 永远命中不了。
所以 `SearchPanel` **长期持有**一个 `LibraryChapterTextSource`，`dispose()` 时才 `close()`。

实测收益：九词平均快 **1.9 倍**，最好 3.0 倍（源气）。

> ⚠️ 不能拿单个查询词下结论：`云岚宗` 只有 1.0x（245 命中 / 245 候选 ——
> 候选本来就少，第二次查时章节表已在缓存里，省不下什么）。
> `LibraryChapterTextSourceTest.chapterTableIsComputedOnlyOncePerSource`
> 用**解析器调用次数**而不是时间来判定，这样不 flaky。

### 4.3 导入时不建章节索引

延续 v0.1.1 的取舍：`parseMetadata` 只读文件头 4 KB，`index()` 要读整个文件。
200 本逐个建索引是几十秒卡顿，只记元信息是一秒的事。
索引留到真正点开那本时再建 → **导入代价与书的本数成正比、与体积无关**。

全库检索的加入不改变这条：跨书检索会为候选涉及的书**按需**建索引（懒建），
用户点「建立索引」批量补齐时是 7.2~10.9 s/本，有进度、可取消。

### 4.4 不想给 `SearchPanel` 加"搜索历史"之类的功能

搜索框就一个输入 + 一个按钮。多一个功能就多一处要维护的地方，
而这个项目当前更需要的是把已有功能做扎实（中文分章 + 全文检索 + 界面打磨），
不是横向铺功能。

## 五、模块归属

| 模块 | v0.3 新增 |
|---|---|
| `qingdu-common` | （无改动） |
| `qingdu-core` | （无改动）—— 解析引擎 v0.3 一个字节没动 |
| `qingdu-store` | `BookStore`（分组 / 时长）、`BookmarkStore`（备注）、`Database`（schema v2）、`SearchStore.searchAll`、`BookChapterTextSource`、`LibraryHit`、`LibrarySearchResult` |
| `qingdu-desktop` | `SearchPanel`（本书/全库双范围）、`LibraryIndexTask`（批量建索引）、`LibraryChapterTextSource`、`LibrarySearchPresenter`、`ReadingTimeTracker`、`BookshelfView`（分组筛选）、书签备注 UI |

**为什么 `LibrarySearchPresenter` 是纯静态类**：
`qingdu-desktop` 的单元测试刻意不碰界面（不依赖图形环境）。
"跨书结果怎么分组""覆盖度怎么措辞"是这段逻辑里最容易错、
又最难通过肉眼发现的部分，所以从 JavaFX 控件里抽出来，17 个毫秒级单测钉住。
