# v0.4 设计文档：AI 问答（基于原文的 RAG）

日期：2026-10-03
上一版：v0.3.0（书库整理 + 全库检索）

---

## 〇、这一版要解决什么

**目标：给轻读加上"基于原文的问答"** —— 用户问"林动这一章讲了什么"，
系统基于他书架上的原文回答，并**给出引用出处**（第几本书、第几章、哪一段）。

**为什么做这个，而不是继续加阅读器功能**：
v0.1~v0.3 做的是"把一本书读顺""把书库管起来"，都是**确定性工具**。
接下来的求职方向是 AI 应用开发，而"三个项目里没有一个是 AI 项目"是当前最大的短板。
轻读有一个别人 seldom 有的东西 —— **一套已验证的中文全文检索层**
（自研二字滑窗分词 + FTS5 + 原文后过滤，四本真书 29 个查询词零假阳性）。
RAG 链路里"检索"正是最容易做糙的一环，把它接上 LLM 是**有真实技术含量**的做法，
不是"给项目贴个 AI 标签"。

**明确不做**：不做"AI 续写"、不做"AI 改写正文"、不做任何**改写原文**的功能。
理由：这是阅读器，不是写作工具。AI 只做**只读的理解与问答**。

## 一、架构：为什么拆成两个进程

```
┌─────────────────────────────┐        HTTP/JSON        ┌──────────────────────────┐
│  轻读（Java / JavaFX）        │  ───────────────────>   │  qingdu-ai（Python）       │
│  · 书架、阅读、界面            │  <───────────────────   │  · FastAPI                │
│  · 检索层：FTS5 + 后过滤      │      引用出处回传        │  · 切分 / 召回 / 重排/ 生成 │
│  · 原文：TXT + 章节偏移        │                        │  · LLM 调用               │
└─────────────────────────────┘                        └──────────────────────────┘
```

### 1.1 为什么不让 Python 自己读文件

轻读的原文在**用户本机的 TXT 文件**里，路径是 Windows 本地路径，
而且定位靠**章节字节偏移**（`startOffset` / `endOffset`）—— 那套偏移是
`qingdu-core` 的 `TxtBookParser` 算出来的，重实现一遍就等于把解析引擎复制一份。

所以**原文一律由轻读喂给 Python**。Python 侧不碰文件系统，只做"文本 → 答案"。

### 1.2 为什么不用 Java 侧调 LLM

技术上可行（加个 HTTP 客户端 + JSON 解析即可，零新依赖也行）。
但**收益不对等**：

- Java 调 OpenAI 接口能写在简历上的只有"我会调 API"，面试聊不出东西
- AI 应用岗真正问的是：切分策略、召回怎么做、rerank 怎么排、幻觉怎么抑制、
  引用怎么保证 —— 这些在 Python 生态里有成熟范式，也更容易做深
- 简历上 "Python + FastAPI + RAG + Agent" 直接命中 JD，
  "Java + HTTP 调模型"命中不了

**代价**：多一个 Python 进程。缓解办法是轻读启动时探测本地 `8000` 端口，
**探测不到就禁用 AI 入口并给出明确提示**，不能让界面因为服务没起而卡住。

## 二、文本切分：章节内按段落切

**决策：最小单元是"章"（`LightChapter`），章内按段落再切 3~5 个片段。**

### 2.1 为什么不是"固定字数滑窗"

512 字 / 50 字重叠是最通用的做法，但在这个项目里有两个具体问题：

1. **会把章节标题切开**。滑窗不管语义，可能从"第一百二十三章"中间开始，
   片段就成了"…百二十三章 林动双眸微闭…"，模型看到的是断头信息。
2. **引用无法定位**。问界面要跳回"第几章"，滑窗给出的偏移是无意义的字节数。
   而按段落切，每个片段都带 `bookId / chapterIndex / paragraphIndex`，
   引用能精确落到"《武动乾坤》第 930 章第 3 段"，点一下就跳过去。

### 2.2 为什么不是"整章一块"

一千多字一章，整章送进上下文的问题是：
- 一章里往往有好几个场景，整章会稀释注意力，模型可能答的是别处的内容
- token 消耗大（中文 1 字 ≈ 1.5 token，一章 1500 字 ≈ 2250 token）
- 提问"第 3 段发生了什么"这种局部问题，整章答不准

按段落切成 3~5 段，粒度就落在"一个场景"这个粒度上，
既不稀释也不碎片化。

### 2.3 片段的数据结构

```python
@dataclass(frozen=True)
class LightChunk:
    book_id: str          # BookId（由路径派生，跨进程一致）
    book_title: str
    chapter_index: int    # 0-based
    chapter_title: str
    paragraph_index: int  # 章内第几段
    text: str
```

**刻意不存 `offset`**：偏移是轻读进程内部的东西，跨进程传它没有意义，
还会让 Python 侧产生"我也能读文件"的错觉。Python 只认 `book_id + chapter_index`。

### 2.4 切分在谁那里做

**在轻读侧切**，不传给 Python 整个文件。
理由：段落是 `ChapterBlock` 的概念（`qingdu-common` 里就有），
轻读切好直接给 Python 结构化数据，Python 不需要重新理解"什么是一段"。

## 三、检索：先只做关键词召回

**决策：v0.4 只用已有的 FTS5 关键词检索召回，向量检索留到 v0.5。**

### 3.1 理由

- **零新依赖、零 API 成本**。embedding 要钱、要网络、要有 key
- **中文短查询上关键词常常比向量更准**。用户问的是"药老在哪几章出现"、
  "云岚宗是什么地方" —— 这些都是**专有名词**，关键词精确匹配比语义相似更可靠
- 轻读的检索层**已经被四本真书验证过零假阳性**，这是现成的、可信的一环

### 3.2 但关键词有明确的短板（所以要留 v0.5 的位置）

问"他怎么变强的"这种**不含专有名词**的问题，关键词召回会召不回任何东西 ——
分词后是"他""怎么""变""强"这些高频词，命中的是满篇都是的段落。
这类问题需要语义召回。v0.4 不假装能处理，**遇到召不回时明确告诉用户**
"没找到相关原文，换个说法或用书名/人名试试"，而不是硬凑一个答案。

### 3.4 🔴 真机验收发现：召回排序缺一环（2026-10-03 已修）

这一节是**四本真书 + DeepSeek 实测逼出来的**，不是设计阶段想到的。

#### 现象

| 问题 | 候选池 | 含答案的段 | 送进上下文的 8 段里含词 | 模型回答 |
|---|---|---|---|---|
| 全职高手 / 叶修 | 156 段 | **66 段** | **0 段** | 「原文里没有提到叶修」 |
| 斗破苍穹 / 药老 | 105 段 | **25 段** | **0 段** | 「原文里没有提到药老」 |

**第一反应会以为模型在幻觉，但它说的是真话** —— 送进上下文的 8 段里
确实一段都不含「叶修」。防幻觉机制工作正常，是**召回侧把答案漏掉了**。

#### 根因

Python 侧 `select()` 第一版只做「去重 + 章节打散 + 截断」，**完全依赖传入顺序**。
而轻读传进来的是什么？是

```
FTS5 命中章 → 取出该章**全部**段落 → 按章顺序排列
```

**不是**「按段落命中次数」排列。于是一章 60 段里，
命中词可能落在第 39 段；而章节打散取的是「每章**前** 2 段」，
于是含答案的段永远进不了上下文。

> 这与 v0.2 时期「四本真书 19/19 查询零假阳性」的结论**不冲突**：
> 那验证的是「命中的都准」（查准率），这里发现的是「该命的没全被选上」（查全率）。
> 两个方向的问题要在同一套数据上分别验证才看得出来。

#### 修法

`select()` 增加 `question` 参数，先按关键词命中数**稳定重排**，再分组打散：

```
pool = _dedupe(…)            # 去重
pool = _drop_empty(…)        # 截超长
pool = _rerank_by_terms(…)   # 🔴 新增：按问题重排（必须在打散之前）
by_chapter = group_by(…)     # 分组
selected = 每章前 2 段 + 轮转补齐
```

**重排必须在打散之前** —— 打散取的是「每组的前 N 段」，
只有先按相关性排好，取出来的才是相关的段。顺序反了等于没重排。

#### 关键词怎么切（这里也踩了一个静默退化的坑）

第一版 `_query_terms` 只是「删标点」，于是

```
「叶修是怎么退役的」→ 整串一个词 → text.count(整串) 恒为 0
```

**打分对长句完全失效，且没有任何报错。** 真机验收时这条路径静默退化，
只有对比「候选池含词数」与「选中含词数」才看得出来。

改成与 `CjkTokenizer` 同一思路的 **n-gram 滑窗**：
中文取 bi~quad-gram（`叶修` `修是` …），ASCII 词整体保留。
无意义的组合（「修是」「是怎」）**按片段集合整体过滤** ——
只保留在至少一个片段里出现过的项。这比维护停用词表省事，且永远列不全的问题不存在。

#### 修复效果（同一批真书数据）

| 书 / 问题 | 候选 | 重排前含词 | 重排后含词 |
|---|---|---|---|
| 全职高手 / 叶修 | 156 | 0 | **8** |
| 斗破苍穹 / 药老 | 105 | 0 | **7** |
| 斗破苍穹 / 云岚宗 | 70 | 1 | **7** |
| 全职高手 / 荣耀 | 80 | 2 | **8** |
| 元尊 / 元尊 | 74 | 1 | 2 |
| 武动乾坤 / 云岚宗 | 147 | 0 | 1 |

模型回答随之改变：叶修 →「陈果网吧的新员工，被使唤搬新键盘」；
药老 →「自称药老，说来历先不告诉萧炎」。

#### 附带的第二个 bug

`_drop_empty_and_oversized` 原本结尾有 `out[:max(top_k*4, top_k)]`，
本意是"限制候选规模"，但它跑在重排**之前** ——
「云岚宗」那例含答案的片段排在第 11 位，被这个"保护性"截断直接丢掉。
**任何在重排之前的截断都会让重排失效。** 已删，改为入口 `MAX_CHUNKS` + 末尾 `[:top_k]` 两处控制。

### 3.5 轻读这层要不要去掉疑问词（真书实测）

轻读的检索词来自 `AskKeyword.of(question)`：去掉疑问词与标点，
剩下的整串交给 `SearchStore`。**为什么不全句直接丢进去？**
因为 FTS5 的 MATCH 是 **AND 语义**（要求每个 token 都出现），
token 越多、越可能出现"原文没有的相邻对"，整条就召不回。

**判据必须用真书量，不能靠推理。** `scripts/kw_probe.py` 用四本真书
（GB18030 编码，见 7.4 的坑）跑 10 个问句，比较两种策略切出的 bigram
有多少在原文真实出现过：

| 书 | 问题 | 去疑问词后 | 去词 token | 整句 token | 结论 |
|---|---|---|---|---|---|
| 全职高手 | 叶修是怎么退役的 | 叶修是退役的 | 5/5 | 7/7 | 一样 |
| 全职高手 | 叶修是谁 | 叶修 | 1/1 | 3/3 | 一样 |
| 斗破苍穹 | 药老是什么来历 | 药老来历 | 3/3 | 6/6 | 一样 |
| 斗破苍穹 | 药老是哪本书的人物 | 药老是的人物 | 5/5 | **6/8** | **去词更好** |
| 武动乾坤 | 林动为什么能修炼 | 林动能修炼 | 4/4 | 7/7 | 一样 |
| 武动乾坤 | 云岚宗在哪里 | 云岚宗 | 2/2 | 5/5 | 一样 |
| 元尊 | 元尊是什么来历 | 元尊来历 | 3/3 | 6/6 | 一样 |
| 全职高手 | 苏沐橙怎么加入嘉世 | 苏沐橙加入嘉世 | 6/6 | 8/8 | 一样 |
| 斗破苍穹 | 萧炎在哪里拜师 | 萧炎拜师 | **2/3** | 5/6 | 一样（都召不回） |
| 武动乾坤 | 林动是谁 | 林动 | 1/1 | 3/3 | 一样 |

**结论：去词不是必需，但无害，且 token 少一半。**

- 只有 1 例**真的靠去词救回来**：「药老是哪本书的人物」—— 整句的
  `哪本` / `本书` 在《斗破苍穹》全文不存在，FTS 直接召不回。
- 有 1 例**去词反而更差**：「萧炎在哪里拜师」删掉「在哪里」后造出
  `炎拜`，原文没有；不过整句缺的 `里拜` 同样不存在 —— 两边都召不回，平手。
- 其余 8 例两边都能召回，但去词后 token 从 6~8 降到 1~5。
  AND 语义下 token 越少越安全，Python 侧重排的计算量也小得多。

⚠️ **两个刻意不删的词**：

- 「谁」**不单独删**（只删「是谁」）。早期版本把「谁」列进词表，
  「谁知道这件事」会被砍成「知道这件事」—— 召不回。
- 「什么」**不删**。删掉后「萧炎用的什么功法」→「萧炎用的功法」，
  少一个 token 但多造出 `的功` 这种通用组合，未必更好。

⚠️ **全角空格 U+3000 要显式处理**：Java 的 `\s` 和 `String.strip()`
都**不含**它，而中文输入法下按空格键打出来的正是全角空格。
漏掉它的现象是检索词里藏一个"看不见的空白"，
送到 FTS 那边就是"一个 token 都没命中"—— 静默失败，不报错。

### 3.6 v0.5 的融合方案（先记下，不现在做）

关键词召回 + 向量召回，用 **RRF（Reciprocal Rank Fusion）** 融合两路排名。
RRF 只需要两个排名序列，不需要把两种分数归一化到同一量纲 —— 这是它比
加权求和更省事的地方，面试时也讲得出理由。

## 四、生成：必须防幻觉

**这是 RAG 最重要的一环，也是面试必问。**

### 4.1 提示词的硬约束

系统提示里写死三件事：

1. **只能依据提供的原文回答**，不得使用自己的知识
2. **每个结论必须带引用编号**，格式 `[1]` `[2]`
3. **原文里没有就说不知道**，明确说"原文里没有提到"，不许编

### 4.2 引用可核对

每个片段带编号（`[1]`、`[2]`…）传给模型，模型引用哪个编号，
轻读侧就能把它变回"《武动乾坤》第 930 章第 3 段"并做成可点击的跳转。
**这不是为了好看** —— 它让用户能验证答案，
也让"模型编了一个不存在的章节"这种错误**立刻暴露**。

### 4.3 服务端也要校验

⚠️ 不能只信模型输出的引用编号。模型可能报一个不存在的 `[7]`。
所以 Python 侧要**把模型返回的编号过滤一遍**，不在传入片段集合里的编号直接丢掉。
最终如果一个有效引用都没有 → 判为"无法回答"，返回失败而不是返回一段没有出处的文字。

**过滤器（`llm.validate`）的三条判定，写死、不含糊：**

| 模型行为 | 处理 |
|---|---|
| 引用编号全部不在片段集合内（含越界高位编号如 `[100]`） | `answer=null`，`reason=invalid-citations` |
| 编号部分有效 | 保留有效部分，**并删掉那些无引用的句子** |
| 引用了有效编号，但那句话的内容其实来自别的片段 | ⚠️ **机器拦不住**，只能靠用户核对原文 |

第二行那条"删掉无引用的句子"是刻意加严的：一段"模型用自己知识补出来"的文字
混在有出处的答案里，**危害比整段拒答更大** —— 用户会以为整段都有出处。
宁可少给内容，不能给出处不明的内容。

⚠️ 引用校验**只能拦住"形式错误"，拦不住"内容错位"**。
这是引用机制的真实边界，不要夸大它。引用真正的价值是**让错误可被发现**：
用户点开引用就能核对——这正是"引用可核对"（4.2）的意义。

## 五、进程间接口

### 5.1 为什么用 HTTP 而不是共享数据库

共享 SQLite 看着省事，但有两个问题：
- **写并发**：轻读正在写进度/书签时，Python 也要写同一库，WAL 下会锁等待
- **职责糊**：一旦 Python 能写轻读的库，"谁是这个数据的主人"就说不清了

HTTP 的好处是**边界清晰**：轻读是数据的主人，Python 是无状态的服务。
而且 HTTP 后面自然能换成本地 MCP server，不影响轻读侧代码。

### 5.2 端点

⚠️ **这里修正了初稿的一个自相矛盾之处。** 初稿把请求写成
`{"question", "bookIds", "topK"}`，同时 1.1 又写"检索层在轻读（FTS5）" ——
这两条**不能同时成立**：检索在轻读侧，就必须轻读先检索完才能发请求，
那么请求体里必须带原文片段，否则 Python 拿不到任何原文，无从作答。

最终形态是「**轻读检索 + 切分 → 传片段 → Python 重排并生成**」：

* 仍然满足「一次问答 = 一次请求」（检索与切分在轻读发请求**之前**完成）
* 仍然满足「Python 不碰文件系统」（片段由轻读喂进来）
* 仍然满足「检索层只有一处」（FTS5 召回在轻读，Python 只做片段级去重/打散/截断）

```
POST /api/ask
  请求：{
    "question": "...",
    "chunks": [ { "bookId":"b1", "bookTitle":"武动乾坤",
                  "chapterIndex":929, "chapterTitle":"第九百三十章",
                  "paragraphIndex":2, "text":"…" } ],
    "bookIds": ["b1","b2"] | null,
    "topK": 8
  }
  响应：{
      "answer": "……[1][2]" | null,
      "citations": [
        { "index":1, "bookId":"b1", "bookTitle":"武动乾坤",
          "chapterIndex":929, "chapterTitle":"第九百三十章",
          "paragraphIndex":2,
          "ref":"《武动乾坤》第 930 章第 3 段", "excerpt":"……" }
      ],
      "coverage": { "searchedBooks":2, "indexedBooks":2, "hits":2 },
      "elapsedMs": 1234,
      "reason": "ok" | "no-chunks" | "invalid-citations" | "llm-error" | "not-configured"
  }

GET /api/health
  响应：{ "ok": true, "llm": "ready" | "no-api-key" | "not-configured", "version": "0.4.0" }
```

**`chunks` 上限 200**：轻读一次可能切出几百个段落，全塞进来请求体会膨胀到几十 MB。
超出按原顺序（= 相关性顺序）截断。

#### 为什么 Python 还要"再排一次"

它**不是**再做一次检索。FTS5 是唯一有检索语义的地方，Python 不重复。
它做三件轻读**不方便做**的事：

1. **去重** —— 轻读可能对同一段落重复命中
2. **章节打散** —— 同章最多取 2 段（`MAX_PER_CHAPTER`）。同一章的相邻段落
   都进上下文既浪费 token，又会让模型过度关注单一场景；不够 `topK` 时用
   各章剩余段**轮转补齐**（round-robin fill），不浪费已召回的原文
3. **截断到 topK** —— 控制 token 预算

在还没有向量的情况下，这一层是**可解释的结构性打散**：每一步都能说清为什么。
v0.5 接上向量后再叠加真正的语义重排。

#### `GET /api/health` 里 `ok` 为什么恒为 true

没配 API key 是**配置问题**，不是服务问题。置 `ok=false` 会让轻读把 AI 入口整个禁用，
而用户实际只需要填个 key —— **过早禁用比明确提示更糟**。
`llm` 字段已经把三态说清楚了。

### 5.3 错误分类

界面要能对不同的失败给出不同的提示，所以错误要分类而不是统一 500：

| 情况 | HTTP | 界面提示 |
|---|---|---|
| 服务没起 | 连接失败 | "AI 服务未启动，请先运行 `python -m qingdu_ai`" |
| 没配 API key | 503 | "未配置模型 API key，设置里填一下" |
| 召不回任何片段 | 200 + `answer=null` | "没找到相关原文，换个说法试试" |
| 引用编号全部无效 | 200 + `answer=null` | "模型没能给出可核对的出处，换个说法试试" |
| LLM 超时/报错 | 502 | "模型调用失败，检查网络或稍后重试" |
| 正常 | 200 | 答案 + 可点击引用 |

**为什么"召不回"和"引用无效"是 200 而不是 4xx？**
它们不是调用失败，而是**有效结论：库里没有能回答这个问题的原文**。
用 200 + `answer=null` 表达，界面才有机会给"换个说法试试，用书名/人名更准"
这种有用的提示；用 4xx 会让它落进通用错误分支。

**服务没起是最常见的情况**（用户不会记住要先开 Python 服务），
所以界面在探测不到服务时就**把 AI 入口置灰并显示怎么启动**，
而不是让用户点了之后才报错。

## 七、验收

### 7.1 必须测的（不测就是没做完）

- **引用编号校验**：模型返回 `[99]`（不存在的编号）→ 全部被过滤 → 判为无法回答
- **无 API key**：返回 503，不是 500
- **召不回**：返回 `answer=null` 而不是编一段
- **切分正确性**：轻读侧切出的片段数量 = 章节内段落数（去掉空段）

### 7.2 真书验收

用四本真书问真实问题，比如：
- "药老在《斗破苍穹》里第一次出现是在第几章？"
- "云岚宗是什么地方？"
- "林动这一章主要讲什么？"（跨片段 + 需要多段上下文）

**判据：引用编号必须能对应到真实存在的章节**（可点击跳转）。
模型答错内容可以接受（那是模型能力问题），**引用错位不可接受**（那是工程问题）。

### 7.3 不变的硬约束

- 轻读**断网仍可用**：AI 服务挂了、没起、没 key，阅读功能一个字都不受影响
- 不引入任何必须联网才能启动的代码路径
- 密钥**不进 git**（`.env` 已在 `.gitignore` 里）

### 7.4 Java 侧接线与三层验收

**接线方式与 `SearchPanel` 完全同构**：面板只认识一个 `Host` 接口
（`currentBook` / `chapterBlocks` / `chapterTitle` / `searchableChapters` /
`jumpToChapter` / `setStatus`），`ReaderView` 里用内部类 `AiHost` 实现。
不做成"面板直接持有 `ReaderView`"——那会让面板认识这个界面两千多行的其余部分。

侧栏第四个 Tab「AI 问答」，菜单入口「搜索 → 基于原文提问…」（`Ctrl+G`）。

**零新依赖**：HTTP 用 JDK 自带 `java.net.http.HttpClient`，JSON 手写
（`com.qingdu.reader.ai.Json`）。为了两个请求引入 OkHttp 会给绿色版加几 MB。

**超时**：健康探测 1.5 s / 问答 120 s / 连接 3 s。界面绝不能因为 AI 服务而卡住启动。

**三层验收，全部已过**：

| 层 | 手段 | 结果 |
|---|---|---|
| Python 侧 | `pytest` | 42 / 42 |
| Java 侧纯逻辑 | `mvn test` | 127 / 127（desktop 模块） |
| 跨进程契约 | `scripts/AiE2eProbe.java` | **23 / 23** |
| 真书 + 真模型 | `scripts/rag_live_check.py` | **12 / 12** |

**为什么还需要第三层（`AiE2eProbe`）**：单测里
`AiServiceClient.interpret` 是直接传 `status` + `body` 的，**完全绕过 socket**。
于是"Java 序列化出的 JSON 与 Python 的 Pydantic 模型对不上"这类故障，
单测一条都发现不了 —— 而它恰恰是双进程架构最可能出的错。
（真踩过：发 snake_case 时 Pydantic **静默丢字段**，请求照样返回 200。）

探针起一个 JDK 自带的 `HttpServer` 当假服务，**端口由系统分配**
（`InetSocketAddress(0)`，不与真 Python 服务抢 8000），
按真实响应结构回 JSON，并把送出的 chunks 读回来回显在引用里 ——
于是能断言"引用能不能映射回真实片段"这个核心判据。

⚠️ **假服务的章名/摘录必须从送来的片段里读，不能写死**：
写死的话那条断言只是在验"假服务和我自己的常量一致"，毫无意义。

### 7.5 三个已知的测量坑

1. **语料是 GBK 不是 UTF-8**。`kw_probe.py` 一开始用 `encoding="utf-8"` 读，
   拿到满屏替换字符，于是连「叶修」都查不到 —— 命中率全是 0，
   看起来像"两种策略都极差"。改 `gb18030` 后才有上表的数据。
2. **PowerShell 会把 UTF-8 子进程输出按 ANSI 解码**。凡是 Python/git 的中文输出，
   都要让 Python 自己 `io.open(..., encoding="utf-8")` 写文件再读回来，
   别拿控制台转存的文件当证据。
3. **测试的期望值会骗人**。`AskKeywordTest` 第一版断言
   `assertEquals("叶修", AskKeyword.of("叶修是怎么退役的"))`，
   跑出来是 `叶修是退役的`。这次是**我写错了**，不是实现错了 ——
   但正是这次失败让我去量了 3.5 那张表，才发现有意义的结论。
   写断言前先问"我凭什么这么期望"。

## 八、这一版不做什么

- **向量检索 / rerank** —— 留 v0.5，v0.4 只做关键词召回
- **流式输出**（打字机效果）—— 先跑通再优化，首版直接返回完整答案
- **多轮对话** —— 先把单轮问答的引用链路做扎实
- **AI 改写 / 续写正文** —— 立场不变，这是阅读器不是写作工具
- **人物关系图谱** —— 技术含量高但不确定性也高，等问答链路稳定再考虑
