# 设计：全文搜索（v0.2.0）

> 本文是**开工前**的设计，四节实测数据都来自 `scripts/FtsProbe*.java`
> （用 `dist\QingduReader\app\*.jar` 当 classpath 跑的，语料是 10.7 MB / 1636 章的《斗破苍穹》）。
> 之所以先探再写：中文全文检索有几个坑**照文档看不出来，只有跑数据才暴露**。

---

## 一、为什么分词方案只能自己写

### 1.1 三个候选，两个不合格

| 方案 | 两字查询（石符 / 林动 / 小貂） | 三字查询（青阳镇 / 聚气散） |
|---|---|---|
| FTS5 默认 `unicode61` | ❌ 全部 0 条 | ❌ 0 条 |
| FTS5 内置 `trigram`（SQLite 3.34+） | ❌ **全部 0 条** | ✅ 命中 |
| **中文 bigram 预切分 + `unicode61`** | ✅ 全部命中 | ✅ 全部命中 |

`unicode61` 不行很好理解：它把连续的一串中文当成**一个** token，
"石符"这种子串自然搜不出来。

**`trigram` 不行则是个真陷阱**。它按三个字滑窗切分，
所以**两字查询根本匹配不到任何 token** —— 而中文里两字词、两字人名
（林动、萧炎、药老）恰恰是最常见的搜法。网上不少「SQLite FTS5 中文搜索」
的教程直接上 trigram，踩了这个坑还以为是自己数据的问题。

实测原文：

```
---- trigram 中文检索 ----
  查「石符」 -> 0 条        查「青阳镇」 -> 1 条
  查「小貂」 -> 0 条        查「聚气散」 -> 1 条
  查「林动」 -> 0 条        查「废物」   -> 0 条

---- bigram + unicode61 ----
  查「石符」 -> [1, 3]      查「青阳镇」 -> [2]
  查「林动」 -> [1]         查「聚气散」 -> [4]
  查「小貂」 -> [3]         查「符文」   -> [5]
```

### 1.2 选定：bigram 预切分

对**连续的汉字串**做二字滑窗，用空格分开后交给 `unicode61`：

```
原文   林动手中的石符，忽然散发出一阵微弱的光。
切分   林动 动手 手中 中的 的石 石符 ，忽然 然散 散发 发出 出一 一阵 阵微 微弱 弱的 的光 光。
```

这样"石符"就是独立 token，两字查询可用；三字查询"云岚宗"切成
`云岚 岚宗`，默认 AND 语义下也能命中。

⚠️ **变体取舍**：第一版把标点也算进汉字串（于是产生 `，忽然`、`光。` 这种噪音 token，
切分后字符数 13.3 M）；改成**只认汉字**（`CJK_UNIFIED_IDEOGRAPHS` 等块）后是 12.05 M，
省约 10%。实现时用「只认汉字」的版本。

### 1.3 后过滤不可省

bigram 把三字词拆成两个 token，FTS5 默认只保证**都出现**，不保证**相邻**。
极端情况下「云岚」在一处、「岚宗」在另一处也会被算成命中。
所以查询后必须拿**原文**再做一次 `contains` 精确校验。

真实语料上的结果（候选 → 精确）：

| 词 | 候选章数 | 精确章数 | 耗时 |
|---|---|---|---|
| 斗之气 | 65 | 65 | 54 ms |
| 药老 | 564 | 564 | 97 ms |
| 萧炎 | 1622 | 1622 | 125 ms |
| 异火 | 554 | 554 | 42 ms |
| 云岚宗 | 244 | 244 | 22 ms |
| 炼药师 | 467 | 467 | 53 ms |
| 纳戒 | 474 | 474 | 46 ms |

这批数据上**候选 == 精确**，说明假阳性实际很少见 ——
但那是运气好，不是设计上可以省。后过滤照做。

⚠️ **探针自己踩过的坑**（记下来别再犯）：把切分后的文本存进被索引的列，
然后又对它 `contains("云岚宗")` —— 切分后是 `云岚 岚宗`，三字词必然 0 命中。
**原文必须单独存（或不存）**，后过滤只能用原文。

## 二、索引粒度：按章，不按段

| 粒度 | 行数 | 建索引耗时 |
|---|---|---|
| 按段落（trigram） | 83,100 | 10.2 s |
| **按章节（bigram）** | 1,636 | 5.9 s（且含 I/O，见下） |

按章还有个语义上的好处：搜索结果**天然就是「第几章」**，
导航直接 `chapterList.scrollTo(index)` 即可，不需要再反查段落属于哪章。

命中位置的高亮/摘要不做在 SQL 层 —— 章节原文只有 6 KB 左右，
从文件读回来后在 Java 里扫子串即可，比 FTS5 的 `snippet()` 更可控（也更好做高亮）。

---

## 三、真正的性能大头是 I/O，不是 FTS

第一轮按章建索引跑了 **37 秒**，看起来像 FTS5 很慢。拆开测才发现：

| 步骤 | 耗时 |
|---|---|
| 循环 `loadChapter`（每章一次 `RandomAccessFile` 打开+seek） | **~23 秒** |
| FTS 插入 | ~14 秒 |

改成**一次性把文件读进内存，再按 `startOffset/endOffset` 字节偏移切片解码**：

```java
byte[] all = Files.readAllBytes(file);
for (Chapter ch : chapters) {
    String raw = new String(all, (int) ch.startOffset(),
                            (int) (ch.endOffset() - ch.startOffset()), charset);
}
```

**83 ms。** 整个建索引 37 s → **5.9 s**。

这正好用上了本项目原有的设计：分章时只记字节偏移，所以任意一章都能从
一次读进来的字节数组里精确切出来，不必逐章开文件。

## 四、表结构定案（第五、六轮实测）

| 变体 | 建索引 | 索引体积 | 查询 |
|---|---|---|---|
| 基准：默认 detail + 存原文（`raw UNINDEXED`） | 5.9 s | 69 MB | 22~125 ms |
| V1：不存原文 + 默认 detail | 5.8 s | 48 MB | 3~14 ms |
| **V2：不存原文 + `detail='none'` + 整表 MATCH（选定）** | **5.0 s** | **33 MB** | **1~14 ms** |

**不存原文是最关键的一刀**：`UNINDEXED` 只是不建索引，内容照样写进 FTS 的内容区，
白占一半空间；而章节原文本来就能靠字节偏移从文件读回来（见第三节，整本 83 ms）。

最终 DDL：

```sql
CREATE VIRTUAL TABLE search_index USING fts5(
    book_id       UNINDEXED,
    chapter_index UNINDEXED,
    body,
    detail = 'none'
);
```

### 4.1 `detail='none'` 的三个限制（实测，不是猜的）

| 能力 | 结果 |
|---|---|
| 整表 `WHERE search_index MATCH ? AND book_id = ?` | ✅ **可用** —— 所以不需要为每本书建一张表 |
| 指定列 `WHERE body MATCH ?` | ❌ `fts5: column queries are not supported (detail=none)` |
| 短语查询 `MATCH '"云岚 岚宗"'` | ❌ `fts5: phrase queries are not supported (detail!=full)` |
| `snippet()` / `highlight()` | ❌ 没有位置信息 |

### 4.2 因此后过滤是**必需的**，不是可选兜底

构造数据实测（真实语料上碰巧没出现，不代表不会发生）：

- 文档 A「他走向云岚宗的大门」→ 真命中
- 文档 B「云岚山中有个岚宗派」→ 含「云岚」「岚宗」两个 token，但**不相邻**

默认 AND 查询 **A、B 都命中**；能区分它们的短语查询在 `detail='none'` 下又不可用。

所以必须在 SQL 之外拿原文再 `contains` 一次。好消息是：
**展示结果本来就要读章节原文来生成摘要**，后过滤几乎是白送的 ——
这也正是选 V2（33 MB）而不是 V1（48 MB）的理由：
反正都要读原文，没必要为"能在 SQL 里做短语查询"多付 15 MB。

## 五、索引时机

不做「导入时建索引」。理由和书架上「导入不建章节索引」完全一致：
索引要读完整本书（5.9 秒/本），用户可能根本不搜这本书。

改为**懒加载**：

1. 用户第一次在某本书里搜索 → 后台 `Task` 建索引，状态栏显示进度（第 n / 1636 章）；
2. 建完落库，之后这本书的搜索都是 22~125 ms；
3. 书的源文件 mtime/size 变了就重建（否则改过的书会搜到旧内容）。

## 六、模块划分

| 模块 | 新增内容 |
|---|---|
| `qingdu-common` | `CjkTokenizer`（中文二字切分）。**订正**：原本计划放 core，实际放 common —— `qingdu-store` 也要用它（切索引文本、切查询串），而 store 刻意不依赖 core（见 store 的 POM 注释）。放 common 才能同时被 core 和 store 用，且不破坏依赖方向 |
| `qingdu-core` | `ChapterTextBatch`：整本读一次、按字节偏移切任意一章（建索引与后过滤共用） |
| `qingdu-store` | FTS 表的建/删/重建，`SearchStore`：索引进度、查询（含后过滤）、失效判断 |
| `qingdu-desktop` | 搜索面板（输入框 + 结果列表 + 命中上下文）、后台 Task + 进度条、点击结果跳转到章节并高亮 |

刻意不放的东西：

- **不放分词相关的第三方库**（IK / jieba 之类）：一是本机代理只放行部分域名，
  下载新依赖有风险；二是 bigram 对"搜子串"这个场景够用且零依赖，
  引入重量级分词器属于杀鸡用牛刀。
- **搜索不做跨书**：v0.2.0 只搜当前打开的书。跨书搜索要处理结果归并和排序，
  留到后面。

## 七、测试计划

单元测试（`CjkBigramTokenizer`）：

- 单字 / 两字 / 三字 / 超长串；
- 汉字与拉丁字母、数字混排（`GB18030`、`JavaFX 25`）；
- 全角标点在汉字串中间与末尾；
- 空串、纯标点、纯空白；
- 切分结果**幂等**（切两次和切一次在查询语义上等价）。

集成测试（`SearchStore`，用临时 SQLite）：

- 建索引后能查到已知词；
- 三字词的后过滤能剔除"两字分处两地"的假阳性（**构造数据**，
  真实语料里不一定出现）；
- 源文件变更后重建；
- 索引不存在时查询返回空而不是抛异常。

真实语料验证（`CorpusProbe` 之后加一步）：

- 四本真书各搜 3~5 个词，记录「候选 → 精确」和耗时；
- 与本文第一节的表对照，确认没有退化。

## 七补、实现阶段补跑的两个探针（结论已落地）

写代码时对 MATCH 串的写法还有两个疑问，看文档答不上来，于是补了 `scripts/FtsProbe7.java` / `FtsProbe8.java`：

| 问题 | 实测结论 |
|---|---|
| 要不要给每个 token 加双引号（防 `and`/`or`/`not` 被当运算符） | **不用**。切分后的文本上 `云岚 岚宗` 与 `"云岚" "岚宗"` 结果完全一致；而 `"云岚 岚宗"`（一个引号里放两个 token）直接报 `fts5: phrase queries are not supported (detail!=full)` |
| 小写 `and` 会不会被当成布尔运算符 | **不会**。小写 `and` 是普通词（命中 `you and me`），大写 `AND` 才报语法错误。而我们的 ASCII token 在切分时已统一折叠成小写，天然安全 |

⚠️ 探针 7 第一版中文查询全是 0 条，别被它误导：那是**插进去的是未切分的原文**（unicode61 把整串汉字当一个 token），
不是查询语法的问题。探针 8 接上分词器后才得到上面这组结论 —— 这正是第一节 1.1 那个坑的现场重演。

## 八、验收标准

1. `mvn test` 全绿（新增测试不低于 15 个）。
2. 10 MB / 1636 章的书：**首次建索引 ≤ 8 秒**且有进度提示；之后查询 ≤ 200 ms。
3. 搜索结果能点进去，跳到对应章节，命中词**高亮**。
4. 索引体积比本文 69 MB 的基准**明显下降**（4.1 + 4.2 至少落地一项）。
5. 四本真书上「候选 == 精确」（零假阳性）。
